1. INTRODUCTION

Hair loss induced by aggressive chemotherapy regimens remains one of the most psychologically challenging and emotionally distressing side effects for cancer patients, severely degrading their self-esteem and mental well-being during recovery. Although thousands of compassionate individuals are eager to donate hair, the lack of a standardized, legally transparent interface bottlenecks connections between donors, non-governmental organizations (NGOs), and verified recipients.

HairFidence is a centralized web-based platform designed to digitalize and streamline the hair donation ecosystem. This SRS document outlines the complete technical, functional, and structural parameters required to develop, deploy, and maintain the system securely.

2. MODULES AND MODULE DESCRIPTION

The system is logically partitioned into four primary user modules, ensuring strict boundaries for data security and role-specific workflows.

2.1 Admin Module

The overarching governance layer for the application.

  • Approve NGOs: Reviews registration credentials and activates NGO accounts.
  • Manage Users & Campaigns: Monitors Donor/Patient profiles and moderates NGO-created campaigns.
  • Resolve Complaints: A ticketing console to view user-submitted issues and update their status to resolved.

2.2 NGO Module

The intermediary layer responsible for medical verification and physical asset logistics.

  • Create Campaign: Deploys local hair donation drives with details (venue, date, description).
  • View Hair Donation Posts: Displays all logged donor hair posts in the system.
  • Verify Hair Donations: Validates incoming physical hair donations and updates status to Donated.
  • Manage Hair Requests: Audits patient requests and approves/rejects them based on medical reports.

2.3 Donor Module

The philanthropic interface optimized for rapid data entry and tracking.

  • Add Hair Donation: Uploads details of the hair (length, texture, photo).
  • View Donation Status: Real-time tracking of the donation pipeline (Available → Processing → Donated).
  • View Campaigns: Accesses the directory of upcoming NGO-led donation events.

2.4 Patient Module

A highly secure, privacy-focused interface for cancer survivors to request wigs.

  • Upload Medical Report: Securely attaches institutional diagnostic reports for NGO validation.
  • Browse Available Hair: An interactive directory to browse and filter verified, available hair donations.
  • Send Hair Request: Dispatches a formal request for a specific hair asset routing it via an approved NGO.
  • View Request Status: Monitors the status of requested hair (Pending → Approved / Rejected).
3. USER STORIES
  • As an Admin: I want to review and approve newly registered NGOs so that only legitimate medical intermediaries can access the verification tools.
  • As an Admin: I want to resolve user complaints to ensure the platform operates smoothly without technical friction.
  • As an NGO: I want to verify medical reports submitted by patients so that resources are allocated strictly to genuine cancer survivors.
  • As an NGO: I want to publish awareness campaigns to encourage community participation in hair donation drives.
  • As a Donor: I want to publish my hair donation details (length, texture, photo) so that it can be matched with a patient in need.
  • As a Donor: I want to track my donation's status so I know exactly when my contribution has been delivered to a patient.
  • As a Patient: I want to securely upload my medical certificates without public exposure to validate my need for a wig.
  • As a Patient: I want to browse a catalog of available hair and request a specific match so I can regain my confidence.

4. FUNCTIONAL REQUIREMENTS

4.1 Authentication & Session Management

  • The system must authenticate users using securely hashed passwords and maintain role-based access control (RBAC).
  • The system must automatically separate user interfaces based on the logged-in role (Admin, NGO, Donor, Patient) using PHP sessions.

4.2 Document Parsing & Auditing

  • The system must enforce mandatory document uploads (Medical Reports for Patients, Registration Certificates for NGOs).
  • The system must hold new NGO accounts in a 'Pending' state until the Admin explicitly toggles their status to 'Approved'.

4.3 Cataloging & Request Handling

  • The system must allow Donors to create posts detailing hair attributes and automatically append a status of 'Available'.
  • The system must lock a donation from the public catalog the moment a Patient requests it, changing its status to 'Processing' to prevent double-booking.
  • The system must allow NGOs to manually finalize a request, updating the specific donation status to 'Donated'.
5. NON-FUNCTIONAL REQUIREMENTS
  • Concurrency Control: The system must utilize atomic database transactions (using MySQL PDO transactions) to prevent race conditions when multiple users attempt to request the same hair donation simultaneously.
  • Data Security & Privacy: Patient medical documents must be strictly isolated. They must never be exposed publicly and are accessible only to the verifying NGO and the Admin.
  • Performance: The application must render primary interfaces and execute catalog search queries within 3 seconds under standard broadband conditions.
  • Usability & Responsiveness: The user interface must utilize a responsive grid framework to adapt seamlessly to desktop, tablet, and mobile device viewports.
  • Reliability & Availability: The platform should aim for 99% uptime, utilizing automated backups to protect the relational database clusters.
  • Maintainability: The PHP backend must be structured with modular routing, ensuring future developers can easily add new modules without breaking existing functions.

6. DATABASE DESIGN (DB SCHEMA)

The platform operates on a highly optimized 8-table relational schema, prioritizing relational data integrity while eliminating unnecessary overhead.

Table Name Primary Key (PK) / Foreign Key (FK) Core Attributes
1. Login login_id (PK) email, password (hashed), role, created_at
2. Donors donor_id (PK), login_id (FK) full_name, phone, address
3. Patients patient_id (PK), login_id (FK) full_name, phone, address, medical_report_url
4. NGOs ngo_id (PK), login_id (FK) organization_name, registration_number, is_approved
5. Hair Donation Posts post_id (PK), donor_id (FK) hair_length, hair_type, image_url, status
6. Hair Requests request_id (PK), patient_id (FK), post_id (FK), ngo_id (FK) request_date, status (Pending/Approved/Rejected)
7. Campaigns campaign_id (PK), ngo_id (FK) title, description, event_date, location
8. Complaints complaint_id (PK), login_id (FK) subject, description, status, date_submitted

This strictly relational schema connects user credentials directly to profile tables via a central login_id foreign key. This ensures that every role transition and data request can be safely authenticated across the entire system infrastructure without data duplication.

7. SYSTEM SPECIFICATIONS

7.1 Hardware Specifications (Minimum Requirements)

  • Processor: Intel Core i3 (or AMD equivalent) and above.
  • Memory (RAM): Minimum 4 GB (8 GB highly recommended for development and server hosting).
  • Storage Space: Minimum 20 GB of free disk space.
  • Network: Continuous Broadband Internet connection for API and Database synchronization.

7.2 Software Specifications

  • Frontend Architecture: HTML5, CSS3, JavaScript (ES6+), Premium CSS variables (custom styling framework).
  • Backend Architecture: PHP 8.x Web Server Engine.
  • Database Engine: MySQL Relational Database (MariaDB) managed via PDO (PHP Data Objects).
  • Development / Hosting Server: XAMPP Control Panel v3.x (Apache Web Server & MariaDB MySQL Server).
  • IDE / Deployment: Visual Studio Code (Development), modern web browser (Chrome/Edge/Firefox) for client access.
